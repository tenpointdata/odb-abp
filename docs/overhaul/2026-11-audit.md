# odb-abp: capability and circumstance audit, phase 1 improvements

Date: 2026-11-02. Scope: `tenpointdata/odb-abp` (fork of `orientechnologies/orientdb`), branch `develop`
at `a13262f` (4.0.0-SNAPSHOT, Java release 17). Phase 1 changes are on branch `ops/overhaul-phase1`.

## Summary

- The codebase is a large, working multi-model database (476k lines of main Java, 249k of tests,
  22 Maven modules) maintained upstream almost entirely by one person (77% of the 2,366 commits since
  2024; dependabot most of the rest).
- Its operational state is weaker than its feature set. The audit found **eight capabilities that are
  currently broken or degraded** on `develop`, most of them recent regressions that fail silently: the
  Docker images can't start the server, the ETL server plugin and Kerberos authentication can't load,
  native OS access silently falls back (512 open files on every Linux host), container memory is
  misdetected on cgroup v2, a remote shutdown leaves every database needing WAL recovery, a failed
  backup reports success, and `dserver.sh` is missing from the distribution.
- Upstream CI passes on the first attempt only **56%** of the time (flaky tests cause 62% of failing
  runs), and its wall-clock nearly doubled in October (about 22 to 41 minutes per job).
- Production runs **3.2.42** (4 masters, ~600 GB, ~290M records) and must upgrade in place to this
  4.0 line. Tested against a real 3.2.42 deployment (section 5): 3.2.42 databases open and give the
  same answers, and 3.2.42 clients work against the new server, but `develop` had three upgrade
  blockers: **Lucene indexes written by 3.2 can't be read** (classes with a full-text or spatial index
  fail reads and writes until `REBUILD INDEX`), the 4.0 console can't connect to any remote database
  (so `backup.sh` and ops scripts fail), and an indexed date comparison that 3.2 answers now throws.
- Phase 1 fixes the eight broken capabilities and two of the three upgrade blockers, and makes the
  Lucene one actionable, plus build, packaging and CI improvements, in 16 focused commits. Nothing is
  removed. Every fix has a test or an end-to-end check in a real container (before/after below).

## 2. Circumstance

### Project and upstream

- Fork created 2026-11-02, public, GitHub Actions enabled, no secrets configured.
- Upstream is active: monthly 3.2.x releases (3.2.57 on 2026-10-05), 378 open issues (distributed
  mode, memory use in Docker and missing metrics are recurring themes), an in-progress refactoring of
  component loading to Java service loaders (October 2026), and WIP branches for Java 21, Hazelcast
  upgrade and distributed refactors.
- Bus factor: one maintainer. The fork should expect to carry fixes and to upstream them selectively.

### Code health and forward compatibility

- `sun.misc.Unsafe` memory access (off-heap disk cache allocator, comparators, binary converter) is on
  the JDK removal path (JEP 471/498): warnings from JDK 24, denied by default in a future release.
  Comparators and converters have safe fallbacks; the direct memory allocator doesn't.
- Hazelcast 3.12 (EOL) underpins distributed mode, the area with most open upstream issues.
- Studio is AngularJS 1.8 + Angular 4 + webpack 3, 93 npm dependencies.
- 1,433 non-script files (mostly Java sources) carry the executable bit.

## 5. Upgrade from 3.2.42 (production)

Production: 4 masters on 3.2.42, ~600 GB and ~290M records per database. Requirement: upgrade in
place to this 4.0 line. `docs/overhaul/upgrade-check/run.sh OLD_IMAGE NEW_IMAGE` checks it end to
end: the official 3.2.42 distribution (checksum-verified from Maven Central) runs as root, as the
upstream images do, and writes a database covering unique/non-unique/hash indexes, Lucene full-text,
a 1,500-edge vertex (edge lists stored as trees), sequences, functions, plus the bundled `demodb`;
then the new image starts on the same database and configuration volumes.

| Check (3.2.42 → this branch) | `develop` as forked | This branch |
|---|---|---|
| Server starts on the 3.2.42 volumes (written by root) | yes, with the upstream image layout; no with the first non-root image ("Permission denied") | yes: the entrypoint hands the volumes over |
| Same answers to 16 queries (counts, unique/non-unique/hash lookups, MATCH, 1,500-edge vertex, sequences, functions, `demodb`) | 14 of 16: the full-text search fails (Lucene 7 index) and the indexed date comparison throws | 16 of 16, after `REBUILD INDEX` of the 6 Lucene indexes |
| Writes on upgraded data | fail on classes with a Lucene index | work |
| 3.2.42 console (binary protocol) → new server | works | works |
| New console → new server / → 3.2.42 server | fails (`connect remote:` is broken) | works / works |
| Messages on first open of a 3.2 Lucene index | `IndexFormatTooOldException`, then an NPE on every search | one error per index naming `REBUILD INDEX <name>` |
| Rollback: 3.2.42 on the volumes written by the new server | | starts and reads everything, including records written by the new server, after rebuilding its Lucene indexes (Lucene 9 files are unreadable by 3.2) |

Upgrade procedure, as tested:
1. Stop the 3.2.42 node cleanly (`docker stop`/SIGTERM or `shutdown.sh`), keep its volumes.
2. Start the new image on the same `databases` and `config` volumes (keep `ORIENTDB_ROOT_PASSWORD`).
3. Rebuild every Lucene index: `select name from (select expand(indexes) from metadata:indexmanager)
   where algorithm = 'LUCENE'`, then `REBUILD INDEX <name>` for each. Until then, searches on these
   indexes fail and so do writes to their classes.

At production scale:
- **Lucene rebuild time is the upgrade's critical path.** `REBUILD INDEX` re-reads every record of the
  class, single-threaded. It has to be measured on a copy of production before choosing between a
  maintenance window and an automatic background rebuild (roadmap). Non-Lucene indexes are read as is.
- A clean stop matters more at 600 GB: an unclean one replays the WAL on start. The remote shutdown
  fix (`d7ba1c9a`) removes the WAL recovery that every `shutdown.sh -u/-p` used to cause.
- Rolling upgrade (3.2.42 and 4.0 nodes in one cluster) isn't verified yet: it's part of the
  distributed catch-up work. Until it is, plan the 4 nodes' upgrade as a full-cluster stop.

## 6. Roadmap

Ordered by operational value. Items marked **decision** need an owner's call before work starts.

1. **Distributed catch-up after short outages** (production's top problem, in progress on branch
   `claude/dist-catchup-ea807f`): the 290 s blocked read during full sync behind the October CI
   slowdown is fixed there, with a Docker harness for a 4-master cluster under write load; the
   mixed-version (rolling upgrade) question belongs to the same work.
2. **Automatic rebuild of Lucene indexes written by 3.x**, through the existing background index
   recreation (`ORecreateIndexesTask`), so the upgrade needs no manual step; measure rebuild time at
   290M records first.
3. **Fix the top flaky tests** (`OCoordinatedDistributedOpsPingTimeoutTest`: injectable clock;
   `OMatchStatementExecutionTest`/`OCommandExecutorSQLSelectTest` setup), and the `tests` module
   slowdown (2-4 min silent gap after `demo_objectschema`), and `LuceneRangeTest`/`OLuceneRangeTest`,
   which fail for 5 days after each DST change. Then the CI re-run can be removed. Also run the
   upgrade check in CI against the 3.2.42 image.
4. **Decision: first start without a password.** Either generate a root password and print it once
   (what the prompt promises; it ends up in container logs) or fail fast with a clear message.
   Also accept `ORIENTDB_ROOT_PASSWORD_FILE` for Docker/Kubernetes secrets.
5. **Readiness and metrics:** an unauthenticated readiness endpoint (storages open, WAL recovery done,
   distributed node online); register the direct memory MXBean; **decision:** package the agent's
   Prometheus metrics in the community distribution or build a minimal exporter.
6. **Low-disk protection:** wire `checkLowDiskSpace` with a positive default threshold and switch
   storages to read-only before the disk fills (behaviour change: configurable, off by default first).
7. **Decision: Studio source.** Build Studio from this repository in the default build (needs
   Node/Yarn in CI) or pin a released Studio artifact, instead of whatever upstream published last.
8. **Script hardening:** `shutdown.sh` (stale PID, no timeout), `server.sh` PID handling, passwords on
   the command line, `orientdb.service` (invalid `ExecStart`, missing `SuccessExitStatus=143`,
   `LimitNOFILE`), `oetl.sh` overriding `JAVA_OPTS`; `-XX:HeapDumpPath`/GC logging in `server.sh`.
9. **Forward compatibility:** add `--sun-misc-unsafe-memory-access=allow` for JDK 23+ in the scripts
   now; plan the move of the direct memory allocator to the FFM API (Java 22+), keeping Unsafe on 17-21.
10. **Distributed security defaults (decision):** TCP/IP members instead of multicast for new installs,
   TLS keystore generation script, bind address variable.
11. **Hazelcast 3.12 → 5.x** (large, coordinate with upstream's `WIP_upgrade_hazelcast`).
12. Hygiene: remove executable bits from sources, dead `jna.version` property and `animalsniffer`
    profile (Java 1.6 signature), orphaned `lucene/config`, `Class-Path: orient-database-enterprise.jar`
    manifest entries.
